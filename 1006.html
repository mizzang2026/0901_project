Supabase와 Vercel로 운영 기능 완성하기

인증 토큰의 역할을 구분하고 DB 마이그레이션 → Edge Function → 프런트엔드 순서로 배포했습니다. 문의·신고, 약관 모달, 관리자 데이터 차트까지 실제 서비스에 연결했습니다.

1. 인증과 연결 2. 배포 순서 3. 운영 기능 4. 관리자 차트 5. 보안 6. 핵심 흐름

1. Supabase 키는 역할이 서로 다르다

.env 파일에 값이 있어도 CLI가 자동으로 읽는 것은 아닙니다. 실행 중인 터미널의 환경 변수로 불러온 뒤 사용해야 합니다.

키사용 위치주의할 점
SUPABASE_ACCESS_TOKENCLI 로그인, 프로젝트 조회·링크·배포새 토큰 발급 시 이 값만 교체
SUPABASE_ANON_KEY브라우저의 제한된 API 접근RLS와 서버 검증을 함께 사용
SUPABASE_SERVICE_ROLE_KEYEdge Function의 관리자 DB 작업프런트엔드와 공개 저장소에 절대 노출 금지

확인 방법: CLI가 Unauthorized를 반환하면 네트워크보다 Access Token의 만료·취소·오입력을 먼저 확인합니다. API의 /health 응답과 CLI 인증은 별개의 점검 항목입니다.

2. 안전한 배포 순서

  1. 로컬 검증 — 프런트 lint와 production build를 먼저 통과시킨다.
  2. 프로젝트 링크 — 프로젝트 ref를 확인하고 로컬 Supabase 폴더를 원격 프로젝트에 연결한다.
  3. DB dry-run — 실제 반영 전에 적용될 SQL 마이그레이션 목록만 확인한다.
  4. DB push — 신규 테이블과 정책을 적용하고 로컬·원격 마이그레이션 이력을 비교한다.
  5. Edge Function 배포 — 새 DB 구조를 사용하는 서버 API를 배포하고 ACTIVE 상태를 확인한다.
  6. 프런트 배포 — 마지막에 Vercel production을 배포하고 운영 별칭 연결을 확인한다.

데이터 구조가 먼저, 그 구조를 사용하는 API가 다음, 사용자 화면이 마지막입니다. 이 순서를 지키면 새 화면이 아직 없는 API나 테이블을 호출하는 시간을 줄일 수 있습니다.

단계오늘 확인한 결과
Database문의와 신고 마이그레이션 적용 및 이력 일치
Edge FunctionAPI 배포 후 활성 상태와 DB 연결 확인
Vercel빌드 성공, production READY, 운영 주소 별칭 연결

3. 사용자와 운영자를 연결하는 기능

  • 1:1 문의 — 사용자가 문의를 남기고 관리자 답변과 상태를 확인
  • 신고 접수 — 게시글·댓글 신고 사유와 상세 내용을 저장
  • 내 신고 내역 — 본인이 접수한 신고만 프로필에서 확인
  • 관리자 처리 — 신고 기각, 게시글 숨김, 댓글 삭제, 처리 완료
  • 이용약관 — 푸터에서 모달로 서비스 이용 기준 안내
  • 개인정보처리방침 — 처리 목적·항목·기간·파기·위탁·권리 안내

권한의 핵심: 사용자의 신고 목록은 요청한 로그인 사용자의 ID와 reporter_id가 같은 데이터만 조회해야 합니다. 관리자 전체 조회 API를 그대로 재사용하면 다른 사용자의 신고가 노출될 수 있습니다.

약관과 개인정보처리방침은 기본 문구만 넣고 끝내는 문서가 아닙니다. 실제 운영자 연락처, 정확한 보유 기간, 외부 서비스와 국외 처리 정보를 운영 환경에 맞게 확정해야 합니다.

4. 숫자를 차트로 바꾸면 상태가 빨리 보인다

관리자 메인 화면에 전체 숫자뿐 아니라 데이터의 변화와 비율을 보여 주는 시각화를 추가했습니다.

시각화읽을 수 있는 내용표현 방식
최근 7일 활동신규 회원, 게시글, 댓글의 날짜별 변화그룹 막대 차트
게시글 구성카테고리별 게시글 개수와 비율도넛 차트와 범례
운영 처리 현황문의 답변율과 신고 처리율, 대기 건수진행률 막대

작은 대시보드는 외부 차트 라이브러리 없이 CSS 막대와 conic-gradient만으로도 만들 수 있습니다. 데이터가 복잡해질 때 전용 라이브러리를 검토합니다.

5. 오늘 확인한 보안 원칙

  1. 비밀키 비공개 — 토큰 값을 터미널 출력, 화면 캡처, GitHub에 남기지 않는다.
  2. 서비스 역할 키 분리 — Service Role Key는 서버에서만 사용한다.
  3. 본인 데이터 제한 — 사용자 API는 인증된 ID를 기준으로 필터링한다.
  4. 배포 전 검증 — SQL dry-run, lint, build를 먼저 실행한다.
  5. 환경 파일 제외 — .env*와 배포 도구의 로컬 설정 폴더를 .gitignore에 넣는다.

오늘의 핵심 흐름

키의 역할 구분 → CLI 인증 확인 → DB dry-run과 push → Edge Function 배포 → 프런트 빌드와 Vercel 배포 → 운영 화면 확인

기능을 만드는 것뿐 아니라 권한, 데이터 공개 범위, 배포 순서, 운영자가 확인할 지표까지 함께 설계해야 서비스가 완성됩니다.
