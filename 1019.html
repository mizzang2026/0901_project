1. 화면에 보이는 결제 정보는 DB에 저장되는가?

실제로 입력한 질문

유저 프로필 페이지에 유저가 결제를 하면 결제정보 (구매, 취소, 환불, 영수증 등) 정보가 있긴 한데 결제 정보가 슈퍼베이스 DB에 연동되고 있어?

화면 코드만 확인하지 않고 실제 Supabase DB를 읽어 저장 여부를 확인했습니다. 프로필은 서버 API를 통해 로그인한 회원의 주문·구독·크레딧 정보를 조회하고 있었습니다.

정보를 저장할 기능이 있다는 것과 실제 저장된 값이 있다는 것은 다릅니다. 환불과 영수증 컬럼은 있었지만 당시 값이 들어 있는 건은 없었습니다.

2. 관리자 결제 조회와 회원별 크레딧 지급·회수

구현·배포 완료

기능을 요청한 실제 프롬프트

관리자 페이지에 결제관련 페이지가 없는데 정보내역 확인 가능하도록 처리해주고, 유저별 관리자가 크레딧 제어할 수 있게 처리해줘. 크레딧은 유저한테 제공 및 회수 등 기능 구현해서 처리해줘.

관리자 콘솔에 결제 관리 메뉴를 추가했습니다. 결제·구독·관리자 크레딧 변경 내역을 20건씩 조회하고, 결제 상태별 필터와 회원 정보, 환불 상세, 저장된 영수증을 표시합니다.

회원 관리 → 회원 검색 → 크레딧 관리에서 지급·회수할 수 있습니다. 결제 내역의 회원 행에서도 같은 관리 화면을 열 수 있습니다.

  1. 대상 회원을 확인하고 지급 또는 회수를 선택합니다.
  2. 수량은 1~1,000,000의 정수, 사유는 2~300자로 입력합니다.
  3. 대상·수량·사유를 확인한 뒤 요청합니다.
  4. 서버가 관리자 권한을 확인하고, DB에서 잔액 변경과 원장 기록을 함께 처리합니다.
  5. 관리자 이력과 유저 프로필의 크레딧 변동에 결과가 표시됩니다.

DB 함수 admin_adjust_credits가 이 작업을 처리합니다. 관리자 조정은 주문 없이 발생할 수 있어 credit_ledger.order_id는 비어 있을 수 있도록 변경했습니다. 결제 주문과 연결된 기존 원장 기록은 유지합니다.

크레딧 회수는 카드 결제 환불이 아닙니다. 계정의 포인트 잔액을 줄이는 작업이며, 실제 결제 취소·환불은 별도 절차입니다.

3. 영수증은 어디에서 확인하는가?

추가로 확인한 질문

영수증 내역 확인가능해?

관리자는 결제 관리 → 결제 내역 → 토스 영수증 ↗, 회원은 프로필 → 결제 내역 → 주문 상세에서 확인합니다.

토스 승인·조회 응답의 영수증 URL을 shop_orders.receipt_url에 저장하고 그 링크를 표시합니다. 우리 DB에 영수증 파일 자체를 보관하는 방식은 아닙니다. 제공된 URL이 없으면 영수증 버튼도 표시되지 않습니다.

‘토스 최신 상태 확인’은 결제 상태와 환불 금액을 토스에서 조회해 DB에 반영하는 기능입니다. 현재 환불 반영은 이 조회 경로를 사용하며, 자동 실시간 웹훅 동기화까지 구현한 상태는 아닙니다.

4. 왜 구독 결제창과 크레딧 결제창은 다른가?

다시 확인한 이해

구독상품은 한번만 결제정보 등록하ㅐ놓으면 자동으로 갱신되는 방식이기 때문에 크레딧 충전하듯 결제하는 방식으로는 적용이 안된다는거지?

일반 결제 한 번을 성공했다고 다음 달 자동 청구 권한까지 등록되는 것은 아닙니다. 일반 결제창으로 한 달 이용권을 판매할 수는 있지만, 그 방식만 사용하면 다음 달에 사용자가 다시 결제해야 합니다.

간편결제 자동결제 추가는 보류

토스페이·네이버페이 자동결제는 별도 심사를 통해 지원됩니다. 오늘은 상점 승인 여부와 전용 연동 안내가 확인되지 않아 실제 등록 경로를 추가하지 않았습니다. 현재 구현은 카드 등록 기반 자동결제이며, 간편결제 자동결제가 완성된 것으로 기억하면 안 됩니다.

5. 이메일이 실제로 있는지, 비밀번호를 잊으면 어떻게 할지

흐름 학습 · 오늘 구현하지 않음

계정 관리에 관한 실제 질문

사용자가 비밀번호를 잊어버렸을 경우 비밀번호 재설정은 어떻게 해야하나

로그인 화면의 비밀번호 찾기 → 가입 이메일 입력 → 재설정 메일 수신 → 인증 링크로 새 비밀번호 설정 → 다시 로그인하는 흐름입니다. Supabase의 resetPasswordForEmail()로 링크를 보내고, 인증된 세션에서 updateUser()로 변경할 수 있습니다.

이메일 검증 질문

회원가입 받을 때 실제로 있는 이메일 주소인지 체크가 가능한가?

이메일 형식 검사는 주소의 모양만 검사합니다. 실제로 메일을 받을 수 있고 사용자가 접근 가능한지는 인증 메일의 링크를 클릭하도록 해서 확인합니다. Supabase의 이메일 확인 기능을 사용할 수 있습니다.

오늘은 두 기능의 원리를 설명한 단계입니다. 비밀번호 재설정 화면을 새로 구현하거나 이메일 인증 설정을 활성화한 작업은 하지 않았습니다. 카카오 계정의 비밀번호 재설정은 카카오에서 진행합니다.

6. 가비아에서 산 mifly.shop을 Vercel에 연결하기

연결 완료

도메인 연결을 시작한 실제 프롬프트

mifly.shop 으로 2200원짜리 도메인 구매했어. 이거를 우리동네 페이지 도메인으로 사용하려면 어떻게해야해?

처음에는 개인 소개·포트폴리오용 이름을 고민했고, 영어 이름 Mifly Jules와 연결되는 mifly.shop을 가비아에서 구매했습니다. 이번에는 우리동네 서비스의 운영 도메인으로 연결했습니다.

  1. Vercel의 0915-board 프로젝트 Domains에 mifly.shop과 www.mifly.shop을 추가합니다.
  2. 가비아 DNS 관리에서 Vercel이 안내한 레코드 값을 입력합니다.
  3. DNS가 반영되고 HTTPS가 정상 제공되는지 실제 접속으로 확인합니다.
타입호스트입력할 값
A@Vercel 프로젝트에서 안내하는 IP
CNAMEwwwVercel 프로젝트에서 안내하는 대상 주소

가비아 네임서버를 사용하면 가비아에서 설정한 DNS 레코드가 적용됩니다. Vercel DNS 관리 화면에만 레코드를 입력하는 것과 구분해야 합니다.

처음 검사했을 때는 www만 정상 접속됐고 기본 도메인은 조회되지 않았습니다. 이후 DNS 반영을 확인했으며 최종적으로 mifly.shop → www.mifly.shop 리디렉션과 HTTPS 접속이 정상 작동했습니다.

7. 도메인을 연결해도 백엔드 허용 주소는 따로 바꿔야 한다

실제 설정 변경과 배포 요청

현재 버셀 및 슈퍼베이스에 이전 버셀주소로 백엔드가 처리된거 같은데 현재 구매한 mifly.shop 도메인으로 주소 변경해서 백엔드 연동 될 수 있게 변경해줘. 그리고 깃허브 및 슈퍼베이스 배포해줘.

사이트는 열렸지만 Supabase API의 Access-Control-Allow-Origin은 이전 Vercel 주소를 반환했습니다. 응답이 HTTP 200이어도 허용 출처가 다르면 브라우저는 응답을 사용할 수 없습니다.

설정반영한 내용
사이트 주소https://mifly.shop → https://www.mifly.shop
백엔드 API 주소https://tbfekmfcbrecdkcaupeh.supabase.co/functions/v1 유지
ALLOWED_ORIGINS새 기본 도메인과 www 도메인 모두 허용. 기존 Vercel·로컬 개발 주소도 유지
Supabase Site URLhttps://mifly.shop

사이트 도메인과 API 서버 주소는 역할이 다릅니다. 프론트엔드의 VITE_API_URL을 무조건 mifly.shop으로 바꾸면 안 됩니다. Supabase API는 그대로 두고 새 사이트가 접근하도록 허용합니다.

카카오 로그인 요청의 복귀 주소와 토스 결제 성공·실패 주소는 window.location.origin을 사용하므로 접속한 도메인에 맞춰집니다. 카카오에서 Supabase로 돌아오는 callback과 Supabase에서 우리 사이트로 돌아오는 callback은 서로 다릅니다.

mifly.shop → Vercel 화면 → Supabase API → DB
카카오 로그인: 새 사이트 → Supabase → 카카오 → Supabase callback → 새 사이트 /auth/callback

Supabase 설정을 변경하고 API를 배포했으며 GitHub 커밋 bc38ae1과 Vercel 배포를 확인했습니다. 브라우저에서 새 도메인의 로그인·프로필·결제정보 조회를 검증했습니다.

8. 관리자 페이지의 ‘로그인이 만료되었습니다’ 해결

문제 상황을 전달한 실제 프롬프트

도메인 변경하고 나서 어드민 페이지 연결이 잘 안되는데 어드민 페이지도 mifly.shop으로 연동되도록 백엔드 확인해줘

추가로 전달한 화면의 문구

댓글 관리 2026년 9월 15일 로그인이 만료되었거나 유효하지 않습니다.

새 도메인의 관리자 API 접근을 점검했습니다. 서버는 유효하지 않은 로그인 토큰을 거부하고 있었는데, 화면은 저장된 관리자 정보와 토큰이 있다는 이유로 메뉴를 표시하고 있었습니다. 그래서 메뉴에 들어가서야 인증 오류를 만났습니다.

  • 도메인별 저장소: 기존 vercel.app의 관리자 로그인은 새 도메인으로 자동 이전되지 않습니다. 새 도메인에서 다시 로그인해야 합니다.
  • 만료된 토큰: 토큰 문자열이 저장되어 있어도 유효한 로그인 상태라는 뜻은 아닙니다. 서버 검증이 필요합니다.
  • 고정 날짜: 화면의 ‘2026년 9월 15일’은 코드에 고정된 표시였습니다. 한국 시간 기준 오늘 날짜를 표시하도록 변경했습니다.
  1. 관리자 화면 진입 시 /api/admin/me로 권한을 확인한 뒤 메뉴를 표시합니다.
  2. 토큰 만료 시점과 관리자 API의 401·403 응답을 감지합니다.
  3. 관리자 세션을 정리하고 /admin/login에서 재로그인을 안내합니다.
  4. 다른 탭을 보다가 돌아왔을 때도 권한을 다시 확인합니다.

네트워크 장애만으로 로그아웃시키지 않고, 이전 토큰의 늦은 오류 응답이 새 로그인까지 지우지 않도록 요청 토큰도 비교합니다. 이번 변경은 만료 후 재로그인 안내이며 로그인 토큰 자동 갱신을 추가한 것은 아닙니다.

새 도메인에서 댓글·회원·결제·문의 관리 API가 정상 응답하는지, 만료되거나 위조된 세션이 로그인 화면으로 이동하는지 실제 브라우저로 확인했습니다. 수정 커밋은 5688549입니다.

9. GitHub·Vercel·Supabase는 각각 무엇을 반영하는가?

결과만 정리하지 않기로 한 이유

오늘도 1019.html 페이지 만들건데.. 프롬프트도 내용에 넣어줘. 그냥 정리된 내용만 보면 잘 기억이 안날때도 있어
대상반영하는 내용
GitHub코드와 변경 이력. 로컬에서 파일만 수정했다고 업로드된 것은 아님
Vercel프론트엔드를 빌드·공개하고 도메인을 배포에 연결
Supabase DB테이블·컬럼·DB 함수 변경을 마이그레이션으로 반영
Supabase APIEdge Function 코드를 별도로 배포
Supabase 설정Auth URL과 API secrets를 관리. 코드 push만으로 모두 바뀌지는 않음

오늘 관리자 크레딧 기능은 DB·서버·화면을 모두 변경했습니다. 도메인 연결은 인증 설정·API 허용 주소를 변경했고, 마지막 관리자 세션 수정은 프론트엔드 변경이었습니다. 학습일지 HTML은 0901_project / 0901-project, 우리동네 앱은 0915_BOARD / 0915-board로 서로 다른 저장소와 Vercel 프로젝트입니다.

검증은 빌드·lint, API 권한 확인, 실제 DB 기록, PC·모바일 브라우저로 나누어 진행했습니다. 테스트 계정과 테스트 데이터는 확인 후 정리했습니다. 결제 환경은 계속 테스트 모드이며 실결제를 수행하지 않았습니다.

다시 볼 파일: docs/shop-payments.md, docs/custom-domain.md, backend/supabase/functions/api/admin-billing.ts, frontend/src/components/AdminBilling.jsx, frontend/src/admin-api.js.

10. 다음에 기억이 안 나면 여기부터

  1. 결제는 어디 저장? 주문은 shop_orders, 잔액은 credit_wallets, 변동은 credit_ledger.
  2. 관리자 지급·회수? 회원 검색 → 크레딧 관리 → 수량·사유 → 확인. 잔액과 이력을 함께 저장.
  3. 영수증 버튼이 없다면? 토스가 제공한 영수증 URL이 DB에 저장되어 있는지 먼저 확인.
  4. 구독창이 다른 이유? 매월 청구를 위한 빌링키 등록이 필요하기 때문. 간편결제 자동결제는 아직 보류.
  5. 새 도메인에서 화면만 뜬다면? DNS뿐 아니라 CORS·Supabase Auth 복귀 주소도 확인.
  6. 관리자 인증 오류라면? 새 도메인에서 다시 로그인. 저장된 토큰의 존재와 유효성은 다름.
